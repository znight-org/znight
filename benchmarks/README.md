# Znight benchmarks

Cold start, memory, dependency injection and HTTP throughput of Znight against NestJS, tsyringe,
InversifyJS and hand-wired servers. The results, the method and the caveats are on the
[benchmarks page](../docs/benchmarks.md) of the documentation; this README is about running them.

The benchmarks are not part of the continuous integration and not of `bun run test`: their
workspaces are only type-checked by `bun run typecheck`.

## Run

```sh
# at the repository root
bun install
bun run build          # the @znight/* packages: the Znight application uses their dist

cd benchmarks
bun run bench          # builds the applications, then every suite (about 40 minutes)
bun run report         # charts, tables and headline numbers of the docs, from results/results.json
```

| Command                | What it does                                                                |
| ---------------------- | --------------------------------------------------------------------------- |
| `bun run build`        | Builds the three applications (`apps/*/dist`)                               |
| `bun run bench`        | `build`, then the `boot`, `di` and `http` suites                            |
| `bun run bench:boot`   | Cold start and memory: 30 starts of every application on Node.js and Bun    |
| `bun run bench:http`   | Throughput and latency: 3 rounds of 10 seconds per application and route    |
| `bun run bench:di`     | Dependency injection alone: 100 and 1,000 providers, 30 processes each      |
| `bun run report`       | Writes the charts and tables of `docs/benchmarks.md` from the results       |
| `bun run report:check` | Fails when the docs are out of date with the results (the docs tests do it) |

A suite replaces its own section of `results/results.json` and keeps the others. Options of
`bun src/cli.ts <suite>`:

- `--runtimes node,bun`: the runtimes (both by default);
- `--variants znight-fastify,nestjs-fastify`: some applications only (ids in `src/variants.ts`);
- `--quick`: a few short runs, to check the setup; the results go to `results/quick.json`
  (ignored by git).

Close what you can before a run (browsers, builds, other benchmarks), keep the machine on power,
and compare applications measured in the same run.

## Layout

```txt
apps/
  znight/      the Znight application; ADAPTER=node|fastify|express|hono selects the server
  nestjs/      the NestJS 12 application; PLATFORM=fastify|express
  baseline/    the same classes wired by hand: dist/{node,fastify,express,hono}.js
src/
  cli.ts       the runner
  variants.ts  the HTTP applications under test
  boot.ts      cold start and memory
  http.ts      throughput and latency (autocannon)
  di.ts        dependency injection (projects generated by di-project.ts in .work/, ignored by git)
  report.ts    charts (charts.ts), tables and headline numbers (highlights.ts) of the docs
results/
  results.json the published results
```

Every application serves the same routes with the same controller, service and repository:
`GET /users/:id` and `POST /users`, whose body is validated by the same Zod 4 schema. The runner
checks every response of a load test: an error or a non-2xx status fails the run.

## Add a framework

1. Add an application in `apps/<name>` (a workspace: `package.json` with `build` and `typecheck`
   scripts) serving the two routes like the others, listening on `127.0.0.1:$PORT`.
2. Register it in `src/variants.ts` (and its name in `FRAMEWORK_NAMES`), and its packages in
   `src/environment.ts`.
3. Run `bun src/cli.ts http --quick --variants <id>` to check it, then the suites, then
   `bun run report`.
