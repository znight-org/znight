# Znight benchmarks

Cold start, memory, dependency injection, HTTP and GraphQL throughput of Znight against NestJS,
tsyringe, InversifyJS, GraphQL Yoga and hand-wired servers. The results, the method and the caveats are on the
[benchmarks page](../docs/benchmarks.md) of the documentation; this README is about running them.

The benchmarks are not part of the continuous integration and not of `bun run test`: their
workspaces are only type-checked by `bun run typecheck`.

## Run

```sh
# at the repository root
bun install
bun run build          # the @znight/* packages: the Znight application uses their dist

cd benchmarks
bun run bench          # builds the applications, then every suite (about an hour)
bun run report         # charts, tables and headline numbers of the docs, from results/results.json
```

| Command                 | What it does                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| `bun run build`         | Builds the applications (`apps/*/dist`)                                                     |
| `bun run bench`         | `build`, then the `boot`, `di`, `http` and `graphql` suites                                 |
| `bun run bench:boot`    | Cold start and memory: 30 starts of every application on Node.js and Bun                    |
| `bun run bench:http`    | Throughput and latency: 3 rounds of 10 seconds per application and route                    |
| `bun run bench:di`      | Dependency injection alone: 100 and 1,000 providers, 30 processes each                      |
| `bun run bench:graphql` | GraphQL: 3 rounds of 10 seconds per application and operation, then in-process measurements |
| `bun run report`        | Writes the charts and tables of `docs/benchmarks.md` from the results                       |
| `bun run report:check`  | Fails when the docs are out of date with the results (the docs tests do it)                 |

A suite replaces its own section of `results/results.json` and keeps the others. Options of
`bun src/cli.ts <suite>`:

- `--runtimes node,bun`: the runtimes (both by default);
- `--variants znight-fastify,nestjs-fastify`: some applications only (ids in `src/variants.ts`, and
  in `src/graphql-variants.ts` for the `graphql` suite);
- `--quick`: a few short runs, to check the setup; the results go to `results/quick.json`
  (ignored by git).

Close what you can before a run (browsers, builds, other benchmarks), keep the machine on power,
and compare applications measured in the same run.

## Layout

```txt
apps/
  znight/      the Znight application; ADAPTER=node|fastify|express|hono selects the server
  nestjs/      the NestJS 12 application; PLATFORM=fastify|express
  baseline/    the same classes wired by hand: dist/{node,fastify,express,hono}.js
  baseline-graphql/  the GraphQL schema hand-wired: dist/graphql-js.js (graphql-js on node:http),
                     dist/yoga.js (GraphQL Yoga standalone)
  znight-graphql/    the Znight GraphQL application; ADAPTER=node|fastify, GRAPHQL_DRIVER=builtin|yoga
  nestjs-graphql/    NestJS 12 with @nestjs/graphql and @graphql-yoga/nestjs; PLATFORM=fastify|express
src/
  cli.ts       the runner
  variants.ts  the HTTP applications under test
  boot.ts      cold start and memory
  http.ts      throughput and latency (autocannon)
  di.ts        dependency injection (projects generated by di-project.ts in .work/, ignored by git)
  graphql.ts   GraphQL throughput and latency: the applications of graphql-variants.ts, the
               operations of graphql-operations.ts, sent and checked by graphql-load.ts (autocannon)
  graphql-micro.ts  GraphQL without HTTP (graphql-micro-run.ts): schema build, execution overhead
  report.ts    charts (charts.ts), tables and headline numbers (highlights.ts) of the docs
results/
  results.json the published results
```

Every HTTP application serves the same routes with the same controller, service and repository:
`GET /users/:id` and `POST /users`, whose body is validated by the same Zod 4 schema. The GraphQL
applications follow [the GraphQL contract](#the-graphql-contract). The runner checks every response
of a load test: an error or a non-2xx status fails the run.

## The GraphQL contract

Every GraphQL application follows it exactly, which is what makes the comparison fair:

- `POST /graphql` with a JSON body `{ query, variables }`, answered `200` and `application/json`,
  on `127.0.0.1:$PORT`. No GraphiQL, no logging, no persisted queries, no JIT, no cache besides the
  document cache of each framework (kept at its default);
- the schema of the [benchmarks page](../docs/benchmarks.md#graphql) (Znight derives it from its
  types), with resolver -> `UsersService`/`BooksService` -> in-memory repositories seeded with
  users 1 to 100 and books 1 to 100, book `i` written by user `((i * 7) % 100) + 1`;
  `books(limit)` returns the first books by id;
- `Book.author` batched by a DataLoader, one `users.findMany()` per request: the users repository
  writes one `findMany` line on stderr per call when `BENCH_COUNT_FIND_MANY=1`, and the runner
  checks, before the runs, that one `books` request makes exactly one;
- `createUser` validates its input with the Zod 4 schema of `POST /users` and returns the user;
- graphql-js 17.0, the copy of the workspace: `bun src/cli.ts graphql` fails when an application,
  or any package of its dependency tree, resolves another copy, or when the workspace installs more
  than one. Yoga (and NestJS with Yoga) executes with `@graphql-tools/executor`, Yoga's default;
  graphql-js and Znight (with or without Yoga) execute with graphql-js `execute`.

The runner sends the three operations of `src/graphql-operations.ts` and checks every response
body (no `errors` key, the expected data, the authors of the seed): one failure fails the run. An
application that cannot run on a runtime declares it in `unsupported` (`src/graphql-variants.ts`):
it is skipped there, and the reason is published with the results.

## Add a framework

1. Add an application in `apps/<name>` (a workspace: `package.json` with `build` and `typecheck`
   scripts) serving the two routes like the others, listening on `127.0.0.1:$PORT`.
2. Register it in `src/variants.ts` (and its name in `FRAMEWORK_NAMES`), and its packages in
   `src/environment.ts`. A GraphQL application goes in `src/graphql-variants.ts` and
   `GRAPHQL_PACKAGES`, and is checked with `bun src/cli.ts graphql --quick --variants <id>`.
3. Run `bun src/cli.ts http --quick --variants <id>` to check it, then the suites, then
   `bun run report`.
